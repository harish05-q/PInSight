# Demo Script

This is a step-by-step walkthrough for demonstrating PInSight end-to-end. Estimated time: 8–10 minutes.

---

## Prerequisites

1. Docker and Docker Compose installed.
2. A `.env` file at the project root with:
   ```
   DATABASE_URL=postgresql+asyncpg://pinsight:pinsight@postgres:5432/pinsight
   DATABASE_URL_SYNC=postgresql://pinsight:pinsight@postgres:5432/pinsight
   REDIS_URL=redis://redis:6379/0
   GROQ_API_KEY=your_key_here
   JWT_SECRET=your_secret_here
   ADMIN_USERNAME=admin
   ADMIN_PASSWORD=admin
   ```

---

## 1. Start the Stack (30 seconds)

```bash
docker compose up -d
```

Wait for all services to be healthy:
```bash
docker compose ps
```

You should see 5 services: `postgres`, `redis`, `api`, `worker`, `frontend`.

Open the frontend at **http://localhost:3000**.

---

## 2. Login (30 seconds)

- Navigate to the Login page.
- Enter `admin` / `admin` (or whatever you set in `.env`).
- Observe the JWT-authenticated redirect to the Dashboard.
- **Talking point**: "Auth uses JWT tokens issued by the backend, stored in localStorage for the demo. All mutating endpoints and endpoints that trigger paid Groq calls require authentication."

---

## 3. Create a Transaction & Show Idempotency (1 minute)

Open a terminal and create a transaction:
```bash
curl -X POST http://localhost:8000/v1/transactions \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"idempotency_key": "demo-key-1", "amount": 249.99, "currency": "USD", "merchant_id": "<merchant_id>"}'
```

Run it again with the **same idempotency key** — observe 409 Conflict.

- **Talking point**: "Idempotency is enforced by a unique constraint on the key. Under concurrent load (tested with 20 parallel requests in k6), exactly one transaction is created."

Navigate to the **Transactions** screen in the frontend to see the new transaction.

---

## 4. Fire a Webhook & Show Deduplication (1 minute)

```bash
curl -X POST http://localhost:8000/v1/webhooks \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"provider_event_id": "evt_001", "event_type": "payment.captured", "transaction_id": "<tx_id>", "payload": {"capture_amount": 249.99}}'
```

Resend the same webhook — observe it's deduplicated (processed exactly once).

- **Talking point**: "Webhooks are deduplicated by provider_event_id. The state machine transitions the transaction from `authorized` to `captured` using optimistic concurrency (version column)."

---

## 5. Create an Incident & Trigger Investigation (3 minutes)

```bash
curl -X POST http://localhost:8000/v1/incidents \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"transaction_ids": ["<tx_id>"], "description": "Customer reported double charge on order #1234"}'
```

Then trigger the agent:
```bash
curl -X POST http://localhost:8000/v1/investigations \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"incident_id": "<incident_id>"}'
```

Navigate to **Incidents** in the frontend. Select the incident in the left panel.

**This is the money shot**: Watch the **Agent Trace Viewer** animate:
- Each tool call mounts with a staggered spring animation.
- The currently executing step pulses.
- Click any step to expand the raw JSON of tool inputs/outputs.
- The final RCA Result Card slides in with a radial confidence indicator.

- **Talking point**: "The agent loop is hand-written — no LangGraph, no CrewAI. It selects tools, calls them, and validates citations against actual tool outputs before returning. The trace is fully persisted: every tool call, its arguments, result, latency, and token count."

---

## 6. Semantic Search via Cmd+K (30 seconds)

Press **⌘K** (or **Ctrl+K**) to open the command palette.

Type "payment timeout" — observe results from incidents and runbooks ranked by vector similarity.

- **Talking point**: "Search uses pgvector for semantic similarity. Embeddings are generated by SentenceTransformer (all-MiniLM-L6-v2) and stored alongside the relational data in Postgres — no separate vector DB needed."

---

## 7. Run the Eval Harness (1 minute)

```bash
curl -X POST http://localhost:8000/v1/eval/run \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"sample_size": 55}'
```

This enqueues an async eval job via RQ. Poll for results or navigate to the **Eval Reports** screen.

- **Talking point**: "The eval harness runs the agent against a labeled ground-truth dataset and reports precision/recall on evidence retrieval, hallucination rate (how often the citation gate fires), and cost per investigation calculated from actual token usage × Groq's published pricing."

---

## 8. Dashboard Summary (30 seconds)

Navigate back to the **Dashboard**. Observe:
- Metric cards with count-up animations.
- Incident counts by status.

- **Talking point**: "The dashboard hits a summary endpoint that aggregates across incidents, transactions, and eval runs."
